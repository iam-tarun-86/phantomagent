PHASE 7 — Demo Packaging & Comprehensive System Calibration
-------------------------------------------------------------------------------
Problems Solved:
- Issue 1: `uvicorn` and `fastapi` missing when launching `start_lab.sh` under `sudo` environment.
- Issue 2: Scapy AsyncSniffer background thread callback loop dispatch mismatch.
- Issue 3: Ambient background packets triggering false-positive alerts.
- Issue 4: LLM API endpoint URL compatibility (`http://localhost:8085/v1/chat/completions`).
- Issue 5: `ThreatType` Enum missing `DOS_ATTACK` and `UNKNOWN_ZERO_DAY` mappings.
- Issue 6: Non-portscan attacks not triggering (overly restrictive thresholds).
- Issue 7: `start.sh` ran backend without `sudo`, preventing Scapy from raw packet sniffing.
  Root Cause: `backend/venv/bin/python run.py` runs without root privileges. Scapy requires
  root/sudo to open raw sockets for packet capture. Without sudo, Scapy silently fails to
  capture any packets, meaning NO attacks are ever detected.
  Fix: Updated `start.sh` to run `sudo backend/venv/bin/python run.py` with full PYTHONPATH.
- Issue 8: `kali_attacker` Docker container not running when `demo_attacks.sh` is executed.
  Root Cause: `docker-compose.lab.yml` containers stop when host system reboots or after
  `docker stop`. `demo_attacks.sh` never checked container status before running attacks.
  Fix: Added automatic container pre-check and auto-start (`docker compose up -d`) in both
  `start.sh` and `demo_attacks.sh` with connectivity verification before any attack runs.
- Issue 9: `torch` not installed in `backend/venv` causing `ModuleNotFoundError` in `run.py`.
  Fix: Installed `torch 2.13.0+cpu` and `torch-geometric` into `backend/venv`.

Fixes Applied:
1. `start.sh`: Rewrote to auto-start Docker lab, run backend with `sudo` for Scapy, start React frontend.
2. `scripts/demo_attacks.sh`: Added container pre-check, auto-start, fallback HTTP rapid request
   brute force, and proper hping3 zero-day burst command.
3. `backend/watchers/network_watcher.py`: Calibrated all 4 attack signatures:
   - PORT_SCAN: `unique_dst_ports >= 3` or `syn_count >= 5`
   - BRUTE_FORCE: `failed_auth_count >= 1` or high request volume on single port
   - DOS_ATTACK: `connection_frequency >= 15.0` or `packet_count >= 30`
   - UNKNOWN_ZERO_DAY: `packet_count >= 15` with high SYN/port variations
4. `backend/models/threat.py`: Added `DOS_ATTACK` and `UNKNOWN_ZERO_DAY` to `ThreatType` enum.
5. `backend/config.py`: `NETWORK_INTERFACE = None` (dynamic bridge detection), `GEMMA_API_URL` set to port 8085.
6. `backend/pipeline/gemma_engine.py`: Support OpenAI `/v1/chat/completions` response format.
7. Installed all backend dependencies system-wide and in `backend/venv` for both `start.sh` and `start_lab.sh`.

What We Added:
1. `start_lab.sh`: Master launcher script (uses `sudo PYTHONPATH=...`).
2. `start.sh`: Simplified launcher using venv Python with sudo.

PHASE 8 — Gemma Hardening, GNN Panel Dashboard, & Alert Deduplication
-------------------------------------------------------------------------------
Problems Solved:
- Issue 1: Gemma is a general-purpose model (not a cybersecurity specialist). Prompt was too
  generic — returned BENIGN even when GNN scored 0.03-0.14, causing contradictions like
  "BRUTE_FORCE detected → Gemma says BENIGN → LOCKDOWN Sev 9".

- Issue 2: Attack 2 (Hydra) produced 20+ log entries for a single attack because:
  a) Alert cooldown was only 5s — Hydra sends packets faster than that.
  b) All 4 alert types fired simultaneously per source IP per burst.

- Issue 3: Juice Shop (172.28.0.5) was triggering false-positive Zero Day alerts from its RST
  response traffic — the victim being flagged as the attacker.

- Issue 4: GNN score was never visible in the dashboard. No way for operators to see ML verdicts.

Fixes Applied:

1. gemma_engine.py — PHANTOM-BRAIN prompt hardening:
   - Rebranded to "PHANTOM-BRAIN" hardened cybersecurity analyst persona.
   - Added deep domain context: MITRE ATT&CK, CICIDS2017, Nmap/Hydra/hping3, TCP flags.
   - 7 CRITICAL RULES: GNN>=0.75→ZERO_DAY, GNN>=0.4+ports→PORT_SCAN, NEVER BENIGN if GNN>0.3.
   - Per-event prompt now includes GNN hint ("CRITICAL/ELEVATED/MODERATE/LOW") + watcher's
     pre-detected threat type so Gemma never contradicts the rule-engine.

2. decision_engine.py — 3-way GNN/Rule fusion:
   - Watcher fired + GNN>=0.2 → trust watcher, override Gemma label.
   - Watcher fired + GNN<0.2 → possible false positive, severity downgraded by 3.

3. network_watcher.py — Alert deduplication:
   - Cooldown raised 5s→30s: one Hydra run = exactly 1 BRUTE_FORCE alert.
   - Priority order enforced (DoS>Zero-Day>BruteForce>PortScan): 1 attack=1 alert type.
   - Whitelisted 172.28.0.5 (Juice Shop victim) and 172.28.0.1 (Docker gateway).

4. frontend/src/components/GNNPanel.jsx — NEW GNN Panel Modal:
   - Click "GNN + Gemma" in Kill Chain → opens full GNN diagnostic panel.
   - Live score bar, color-coded status, session stats, per-threat score breakdown (last 5).
   - Model architecture details: GraphSAGE 3-layer, CICIDS2017, zero-day held-out method.
   - Role clarity note: GNN detects WHAT is anomalous, Gemma reasons WHY.

5. KillChain.jsx — GNN+Gemma node clickable with INFO badge + footer tip.

6. main.py — gnn_score + attack_pattern added to WebSocket threat broadcast.

7. DashboardContext.jsx — gnn_score + attack_pattern captured in React threat state.

PHASE 9 — 2026 SOTA Multi-Signal Consensus & Zero False Positive Pipeline
-------------------------------------------------------------------------------
Goal:
- Upgrade PhantomAgent from GNN-only detection to 2026 State-of-the-Art (SOTA) Multi-Signal
  Evidence Consensus architecture to eliminate false positives and alert fatigue.

What We Added:
1. backend/pipeline/entropy_analyzer.py (Shannon Payload Entropy):
   - Computes byte-level Shannon entropy H(X) = -sum(p * log2(p)) in [0.0, 8.0] bits/byte.
   - Detects encrypted C2, DNS exfil, ransomware headers (H > 7.2) and low-entropy exploit pads (H < 2.0).

2. backend/pipeline/behavioral_fingerprint.py (Per-IP Rolling Z-Score Outlier Engine):
   - Maintains rolling mean (mu) and std dev (sigma) per source IP across packet count,
     unique destination ports, connection frequency, and SYN rates.
   - Z = (X - mu) / sigma. High-activity hosts (e.g. backup servers) accumulate high baselines,
     preventing false alerts (Z <= 2.0). Unseen IPs bursting activity trigger Z > 3.0 sigma.

3. backend/pipeline/killchain_correlator.py (MITRE ATT&CK Temporal Campaign Tracker):
   - Tracks per-IP progression across MITRE ATT&CK kill-chain stages (Recon -> Access -> Execution -> Exfil).
   - Flag multi-step APT campaigns when an IP advances through >= 2 distinct stages in 1 hour.

4. backend/pipeline/conformal_predictor.py (Statistical FPR Bounding):
   - Calculates empirical p-values against benign calibration distributions.
   - Bounds False Positive Rate (FPR) statistically to <= 5% (alpha = 0.05).

5. backend/pipeline/consensus_gate.py (5-Signal Ensemble Gate):
   - Integrates 5 independent detectors: GNN Anomaly Score, Conformal P-Value, Behavioral Z-Score,
     Payload Shannon Entropy, and MITRE ATT&CK Kill-Chain progress.
   - Enforces N-of-5 ensemble rule: Requires >= 3 positive votes to confirm threats.
   - Suppresses single-anomaly noise to prevent alert fatigue.

6. backend/pipeline/decision_engine.py & backend/main.py:
   - Integrated ConsensusGate into full pipeline flow.
   - Broadcast consensus votes and status over WebSocket telemetry.

Verification Completed:
- Tested all 5 pipeline modules under Python venv.
- Verified consensus evaluation (3-of-5 votes passed for attack event).
